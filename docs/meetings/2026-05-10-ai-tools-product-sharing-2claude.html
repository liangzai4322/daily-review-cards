Topic 01
主持人的 AI 自动化工具实践
  • 通过 Claude Code 口述需求，快速做出各类小工具和插件
  • 利用 Gemini 免费额度多账号注册，免费跑通 AI 工具
  • 爆款视频爬取工具：定时抓取对标账号爆款，飞书多维表格展示，支持播放量筛选
  • 微信群聊天记录桌面工具：一键获取并 AI 分析，生成每日日报
  • 公众号内容日报：定时抓取关注博主文章，AI 提炼高价值内容自动推送
  • AI 代码自我检查的坑：单层自检无效，需设计三层独立 Agent 检查机制
  • 三维度个人日报：飞书妙记语音、Claude Code 对话记录、微信24小时聊天记录
  • 本地语音识别模型：绕过飞书妙记分钟数限制，自建本地转写模型
  • 小红书视频下载工具：无需 API，丢链接即下载，已做成 Windows/Mac 双版

主持人提到，自己最初是"通过做油管视频的时候开始接触到，然后就做了一些自动化的程序"，对于没有编程基础的人来说，能用 Claude Code 口喷需求就做出插件，当时"非常兴奋"。在爆款视频爬取工具上，他将抓取频率从每天6次调整为每天1次，并在飞书多维表格中用颜色标注新增爆款与持续上榜内容，方便团队快速跟进热点。

在 AI 代码质量保障上，他踩过一个典型的坑——让 AI 自我检查代码质量"只是走一个形式，他并没有真正的去做"，因为模型自写自检根本无法客观验证。后来他咨询 Claude Code，得到的解法是引入独立的第三方 Agent 做检查，并最终设计成三层检查机制，显著提升了输出质量。他还将飞书妙记语音复盘、Claude Code 每日对话、微信24小时聊天记录三者结合，让 AI 全面了解自己当天的工作进程并生成日报，实现了高度个人化的 AI 助理体系。

Topic 02
企业知识库搭建与变现
  • 老板端用 Obsidian（OCD）沉淀公司全量知识，员工端用飞书分级访问
  • 销售、运营部门数据分开管理，但部分信息打通
  • 通过 Claude Code + Bridge 搭桥，让员工通过微信/飞书直接调用大模型
  • 变现方式：知识库交付 + 按小时咨询，客户来源为朋友介绍和公众号
  • 业内行情：企业知识库交付单价可达2万+

主持人提到，他帮一家企业搭建知识库时，"帮他们把整个链路基本上都聊通了"。方案设计上，老板使用自己的 Obsidian 终端，可自动从飞书同步公司所有员工沉淀的数据，形成包含公司全量信息的私有知识库；而员工只能看到飞书上属于自己权限范围内的公开内容，实现了数据的分级管理与权限隔离。

在更进一步的规划中，他还计划为企业部署一个本地大模型，通过 Bridge 搭桥后，每位员工都可以用手机通过微信或飞书调用该模型，同时各部门有自己专属的知识库与之对接。目前这一方向已实现了两笔变现，分别是一个知识库交付单和两个咨询单，咨询按小时收费，客户来源于朋友介绍和公众号文章。现场也有人提到，业内有教练给企业搭知识库收到了2万多元，印证了这一方向的商业价值。

公众号矩阵与账号管理
  • 主持人曾运营200个公众号账号，目前沉淀60多个，以流量组为主
  • 受封号影响，现已停止大规模接广告，转为低频接单
  • 计划做 AI 主题矩阵号，借助已有账号资源快速起量
  • 公众号实名注册有第三方渠道（类似 Claude 账号注册逻辑）
  • AI 工具账号封号问题：Claude 等海外工具封号频发，建议用苹果礼品卡订阅、注册时间长的老账号更稳
  • 自动推送内容到公众号接口易触发封号，建议通过中间号中转再手动复制到主号

主持人坦言，自己曾经做公众号做到200个账号，"后面因为接了一些广告，有些封号了什么的就没做了"，现在沉淀下来的60多个账号以流量组合作为主，偶尔接广告。受追觅老板案例启发，他计划将这批账号转型为 AI 主题矩阵号，认为如果能做50个 AI 方向的公众号，接广告的收益会相当可观。

账号实名的问题是扩张的主要障碍，但他提到"也有渠道，像非洲老哥他们也可以实名"，这与 Claude 等海外工具的账号注册逻辑是一样的。在 AI 工具账号稳定性方面，他目前 Claude 账号注册已有两三年，一直用苹果礼品卡订阅，因此暂时没有遇到封号问题；而自动推送内容到公众号的 API 接口则是另一个雷区，"已经很多号被封掉了"，他现在的做法是先发到一个中间号，再手动复制到主号，以规避风险。

Topic 04
星辰：Workbody 训练与企业 Skill 工作流
  • Workbody 是腾讯出品的国产 AI 工具，本质与 Claude Code/Cursor 类似，内置丰富官方精选 Skill
  • 自训练 Business Flow：从4月14日训练到4月22日，历时7天完成整套企业客资处理工作流
  • 5个执行节点：① 公司背调与简报 → ② 客户资料分析（IT认知水平判断）→ ③ 需求清单输出 → ④ 功能架构图 → ⑤ 业务流程图
  • 人机协同模式：客户30-40分钟沟通后，将需求丢给 AI，开完会方案已输出，直接交给销售
  • IT认知水平判断：高水平直接讲技术，低水平则评估是否值得跟进
  • Skill 训练方法：逐节点测试 → 固化格式 → 嵌套 MD 文件调度子节点
  • Workbody 独有优势：能抓取其他工具（Hama、Web Search）抓不到的微信公众号数据

星辰提到，他"是从架构的角度去出发，就整体规划的角度去出发，来去用 AI 的"。他在 Workbody 中内置了一套自训练的 Business Flow Skill，只需发送一段唤醒词，AI 就会按照固定的5个节点依次执行，并在每个节点等待人工确认后再推进。整套流程用了7天时间从零训练完成，此后每次执行都高度一致，"跟手术刀一样的，它能切中我的12345678点"。

这套工作流的核心价值在于大幅压缩售前时间：他每天接2到3个客资，与客户线上沟通30至40分钟后，将需求丢给 Workbody，等开完会方案就已经出来了，直接交给销售跟进，自己就可以出来参加聚会。Skill 的训练方法是逐节点打磨，确认输出格式后固化，最终通过一个嵌套结构的 MD 文件统一调度所有子节点。他还特别指出 Workbody 的独特之处——它能抓取其他工具无法获取的微信公众号数据，"你别管他是怎么拿的，他就是能拿到你别的拿不到"，这使得它在信息搜集环节具有明显优势。

Topic 05
Hama（本地 AI Agent）部署与使用
  • 部署在火山引擎云服务器（约2000元/年），接入 DeepSeek V4 API
  • 通过飞书 BOT 进程与终端 CLI 双窗口并行：飞书端仅聊天，终端端拥有最高管理员权限
  • 自训练让 AI 独立接收飞书消息并用独立子进程处理，避免任务阻塞
  • 30秒无回复自动发送"处理中"消息，解决长任务无响应问题
  • Hama vs Open WebUI：Open WebUI 存在后台偷跑 Token 的问题，Hama 不发消息则不消耗
  • 用于 AI 辅助内容创作：先写大纲确认，再生成正文，自动存入飞书云文档
  • 要求 AI 每次操作后自行记录日志，防止"说谎"（声称已完成但实际未执行）

星辰介绍，Hama 本质上与 Open WebUI 类似，都是在服务器上运行的 AI Agent 框架，但他选择 Hama 的重要原因是 Open WebUI"会偷偷摸摸吃我的 Token，你知道吗？我很不爽"——即便当天没有发任何消息，Open WebUI 也会在后台消耗 Token，而 Hama 则不会。他将 Hama 部署在火山引擎的云服务器上，接入 DeepSeek V4 的 API，并与飞书打通，"我就给他丢了个飞书文档，我说哥们，你自己把飞书接上，我在那跟你聊天就行了"。

在架构设计上，他实现了飞书端与终端 CLI 的双窗口并行：飞书端的 AI 只能聊天，不能修改服务器配置；终端端的 AI 拥有最高管理员权限，可以执行代码和文件操作。为了解决长任务执行期间 AI 无响应的问题，他训练 AI 自建了一个子进程监听对话，"如果30秒内没给我回话，你先默认，先给我回一条，防止我催他"。此外，他还强调要求 AI 在每次完成操作后都自行记账，因为 AI 存在"说谎"的情况——"他告诉你他干了，实际没干"，通过日志核查可以有效规避这一问题。

Topic 06
AI 工具使用技巧与通用坑点
  • 不要跟模型说废话：描述要像手术刀一样精准，废话越多 AI 越理解不了
  • AI 自检无效：需引入独立第三方 Agent 做质量检查
  • AI 会"说谎"：声称已完成但实际未执行，需通过日志验证
  • 内置工具不可信：Agent 自主调用的插件未必能拿到数据，需逐一测试并禁用无效工具
  • 长任务无响应：需训练 AI 自建进程定时汇报进度
  • C 盘占满问题：Claude Code 等工具默认将文件存入 C 盘，需明确告知 AI 改存 D 盘
  • 多工具分工协作：每个工具只做一件事，避免单一工具承担过多任务导致记忆混乱
  • 模型选择影响效果：底层模型能力不足时，再好的框架也难以执行复杂任务

星辰总结了他在实践中积累的核心经验，其中最重要的一条是"不要跟模型说废话"——"就是你给他的描述要跟手术刀一样精准……你跟他说的废话越多，他越理解不了你。"他的所有指令都极度简洁，只告诉 AI 要什么、怎么做，其余的都是 AI 自己考虑的事。

另一个高频踩坑点是 AI Agent 的工具可信度问题。现代 Agent 会自主决定调用哪个插件，但很多内置插件在特定场景下根本拿不到数据，"他的工具不可信，你得自己去测试你要的场景下他哪些工具能完成"。遇到无效工具，他的做法是直接告诉 AI 在该场景下禁用它，让底层永久记住。此外，小林（说话人3）提出了 C 盘被占满的问题，星辰给出的解法简单直接："你就直接告诉他，你说以后我的所有文件你存在 D 盘的某个文件夹，他自己就干了，就这么简单。"多工具分工协作也是星辰反复强调的原则，"我不会让他去单用一个一个东西的"，每个工具只做一件事，避免因任务过重导致 AI 记忆混乱、输出质量下降。

核心原则：与 AI 沟通要像手术刀一样精准；多工具分工明确；对 AI 的每一步输出都要做验证，不能盲信。

AI 生成 PPT 的心得
  • Workbody 可直接生成可编辑的 PPT 文件（非图片），质量"完全够用"
  • 星辰让 Workbody 给自己写使用说明书并生成培训 PPT，全程只用文字沟通
  • Claude + Claude Design 也能生成高质量 PPT
  • 网页版 AI PPT 工具效果同样出色
  • AI PPT 已可商业化：星辰用此为企业做内训，收取培训费

星辰展示了一份用 Workbody 生成的培训 PPT，内容是"怎么使用 Workbody 的培训教程"，"全程我只跟 Workbody 这个文字"，最终输出的是可以直接编辑的 PPT 文件而非图片，现场众人评价"质量相当可以，起码够用"。他计划用这份 PPT 给前公司同事做付费培训，收了培训费后直接让 Workbody 自己给自己写说明书，省去了自己做 PPT 的时间。

主持人也补充了两个心得：一是 Claude 配合 Claude Design 能做出质量很高的 PPT；二是现在有一些网页版的 AI PPT 工具效果也非常好。这一话题让大家意识到，AI 生成 PPT 已经具备了相当的商业落地价值，可以直接用于客户培训和内训交付场景。

Topic 08
龙伟：Codex 爬虫与自动化应用
  • 百度网盘视频文稿批量导出：Codex 写脚本，发文件夹路径即可批量提取字幕文本
  • 付费网站数据采集：采集低粉爆款公众号标题，按27个领域分类，用于分析爆款规律
  • 爆款标题库 + AI 生成：将采集的爆款标题交给 AI 汇总规律，后续写文章时基于标题库生成
  • 猫咪休息提醒工具：参考 Chrome 插件创意，用 Codex 实现全平台定时弹窗强制休息
  • Codex 能力上限高：龙伟表示"目前为止我让 Codex 做的事情只有我没有想到的，没有它做不到的"

龙伟分享了他用 Codex 实现的几个让他"特别震撼"的应用。第一个是百度网盘视频文稿的批量导出——他原本需要手动逐个点开客户端导出字幕，后来让 Codex 写了一个脚本，"我只要把一个文件夹的位置发给他，他直接就可以帮我导出"，拿到文本后再丢给 NotebookLM 配合 Claude 生成问题、定位原文，形成一套高效的课程学习工作流。

第二个应用是爬取付费网站的低粉爆款公众号数据，该网站按27个领域分类，月费仅10元，他让 Codex 将所有爆款标题采集出来，计划通过 AI 分析总结爆款标题的核心规律，未来写公众号时直接基于这个标题库生成内容。第三个则是一个有趣的"猫咪强制休息"工具——他参考了一个爆火的 Chrome 插件的创意，告诉 Codex 插件名称，Codex 自己找到插件、理解逻辑，并用 Utilities 工具将其实现为全平台定时弹窗，"我甚至都没有告诉他插件的地方在哪"，电脑启动后自动运行，每隔一段时间强制弹出猫咪画面提醒休息。

Topic 09
个人知识管理与"日醒" Skill
  • 微信语音发给 Open WebUI（小龙虾）：实现语音记笔记、积分系统管理、灵感即时记录
  • 积分系统：做了某些事奖励积分（内啡肽），刷抖音等消耗积分（多巴胺），积分耗尽则禁止该行为
  • 课程学习工作流：视频文稿 → NotebookLM → Claude 生成问题 → 定位原文 → 掌握知识
  • "日醒" Skill：每日收集复盘文件、Flomo 笔记、飞书录音，统一处理后分入5个库
  • 5个库：选题库、素材库、弹药库、人设库、认知库（源自俞飞轩分享的框架）
  • 全局 Skill vs 局部 Skill：日醒 Skill 为按需调用的局部 Skill，每晚11点左右手动启动
  • 最终配合 Claude 做深度复盘，基于当天所有内容生成洞察

    • 龙伟分享了他围绕个人知识管理搭建的一套完整系统。日常输入端，他通过微信语音向 Open WebUI（小龙虾）发送笔记、记录灵感，后者还接入了他自建的积分系统——完成有益行为奖励积分，刷抖音等消耗积分，形成一套行为管理机制。在课程学习上，他将视频文稿导出后发给 NotebookLM，再让 Claude 生成问题，NotebookLM 能直接定位到原文位置，让他在得到 AI 浓缩答案的同时也能看到原始表述。

    在输出端，他设计了一个名为"日醒"的 Codex Skill。每天晚上，他将当天的复盘文件、Flomo 笔记、飞书录音统一放入一个收件箱文件夹，然后调用日醒 Skill，它会自动将所有内容按"选题、素材、弹药、人设、认知"五个维度分类存入对应的库，这一框架来自此前参加的俞飞轩分享活动的启发。最后，他再与 Claude 进行深度对话，基于当天积累的所有内容做复盘，形成真正有深度的每日反思闭环。

    蔡一航：站外推广自动化（RPA）
    • 用 Code 叉（Cursor）编写 RPA 脚本，自动将帖子内容填入目标网站表单
    • 解决痛点：公司每天需上70-80个帖子，人工操作耗时1-2小时
    • RPA 局限：无法抓取配图，需从后端直接读取；有机器人认证的网站无法使用
    • 工具组合构想：Cursor（后端）+ Minimax（前端）+ Claude Code（流程调度），三者结合
    • 本地部署方案：家里留一台电脑常开，出门用手机通过飞书控制
    • 计划接入 API 中转站（爱坤客），集中管理多种模型的 API 版本和消费
    • 受星辰启发，计划通过飞书聊天直接控制本地电脑写代码

    蔡一航分享了他用 Code 叉为公司站外推广业务开发的 RPA 自动化工具。公司每天需要向目标网站发布70到80个帖子，人工操作耗时一两个小时，他用 Code 叉写了一个脚本，"它就会自动，它会把信息单自己填上去了"，从后端直接读取帖子内容并自动提交，大幅节省了重复操作时间。RPA 的局限在于无法处理需要机器人认证的网站，以及配图需要从后端直接抓取而非粘贴复制。
